## 1. 分层：为什么不用白皮书的四段式

白皮书第五章给的是 **Ingestion → Normalization → Calendar → Scoring**。这是按**执行顺序**切的，
不是按**依赖方向**切的。直接照建会出三个问题：

- 日历规则既读外部数据、又参与打分 ⇒ 同时被上下两层依赖，单向依赖破功；
- "归一化"与"算 Z-Score"混在一段里，窗口参数与阈值散落各处 ⇒ 无法单独验证；
- 打分层没有前置验证手段，而白皮书恰恰零回测。

**采用方案**：按三条原则重新切 —— 变化频率、依赖方向、能否单独验证。
落到 L0–L7 + 横向重放骨架（见 `docs/正式项目分层架构设计.md`）。

**附带硬约束**：L2–L5 必须是纯函数 + 显式日期参数，不读"现在"。这是重放能成立的前提。

## 2. 几个关键取舍

### 2.1 日历为什么拆成两处

第 3 个周五是**纯日期事实**（→ L0 `clock`）；"OPEX 期间算 6 分"是**业务判断**（→ L3/L4）。
放一起会让日历模块同时被上下两层依赖，正好是第 1 节要避免的破功。

### 2.2 `fill_flag` 为什么是硬要求

白皮书说"前向插值保证时序无跳空"。问题在于：**填充值如果被当成观测参与 Z-Score 与 Δ 计算，
滚动统计量会被静默污染**，而且看不出来。

实测确认这不是理论风险：`WALCL` 停在 2026-10-07，滞后 8 天。按白皮书"填充后算 5 日变动率"，
该变动在多数交易日里其实是同一批周度数据的重复计算。

打标之后，下游才有机会说"这个 Δ 只对周度更新节点有意义"。

### 2.3 重放骨架为什么必须早于 L3/L4

白皮书零回测。**没有重放能力，就无法给任何阈值提供证据** —— 先有尺子再量东西。
把它排在 L3 之前，是为了让 L3 的因子一出生就能被历史检验，而不是等系统全建好再回头补。

它**不是一层**，而是与 L2–L5 并列的消费者，不修改它们。

### 2.4 `gamma_proxy` 为什么放最后

它是白皮书的核心创新，也是最大风险：PCR → 做市商 Gamma 是**弱因果推断**
（PCR 是成交量合约数之比，不含持仓方向），且"机构买指数 Put、散户买个股"的归因假设
会被 0DTE 占比上升、covered-call ETF 规模扩大污染。

把最大不确定性放在最前面 ⇒ 后面全是返工。所以先做三个物理机制直白的维度。

### 2.5 为什么 L7 是分发边界

ICE 的限制是**分发**限制，不是**使用**限制。内部计算照用不误，出口只有一个地方，
管住这一个地方就管住了合规风险。

### 2.6 单一真值归属

- 阈值 **只**出现在 L4 配置
- 权重 **只**出现在 L5 配置
- 仓位比例 **只**出现在 L6 配置

权重和 = 100.00% 做成**启动断言**，不是文档里的一句话 —— 白皮书把它写成了"算术自洽校验"，
那是承诺，不是机制。

### 2.7 单位为什么在 L1 声明、在 L2 换算

L1 只负责"贴上单位标签"（来自配置，不靠猜）；换算需要**目标单位**，那是业务决策，属 L2。
如果 L1 就换算掉，L1 就得知道业务目标，接入层不再通用。

## 3. 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 照白皮书四段式直接建项目 | 按执行顺序切层，会破坏单向依赖；且打分层无前置验证 |
| 按"数据源"分层（FRED 层 / CBOE 层…） | 源会增删，不该成为架构轴。换源应不影响上层 |
| 把因子计算与打分合成一层 | 阈值标定需要独立于计算。合成后改一条阈值就要动计算代码 |
| 回测做成独立旁路脚本 | 会与主链路分叉，形成两套真相。改为横向骨架**复用** L2–L5 |
| 在 L1 做单位换算 | 换算需要目标单位（业务决策），L1 会因此不再通用 |
| 硬把 Flip Point 做出来 | CBOE PCR 是聚合量，无行权价 / 到期日 / 持仓分布。**数据不支持，宁可删指标** |
| 用 `display_url` 参数做脱敏 | 已实现在 `net.py`，但异常链仍会带出 `HTTPError.url`。改为 `secrets` + `from None` |

## 4. 踩过的坑（下次直接绕开）

### 4.1 FRED 首次 key 失败，但格式完全合法

32 位、纯小写字母数字、无 BOM、无隐藏字符 —— 全部通过，FRED 仍回
`The value for variable api_key is not registered`。
**教训：只验格式不够，必须直接打一次原始请求看服务端是否认。** 换 key 后立即 200。

### 4.2 HTTP 错误的响应体被丢弃

`urllib.error.HTTPError` 只给了状态码，原因在 `exc.read()` 里。
丢弃它 ⇒ 只看到 400，看不到"key 未注册"。**必须把响应体附进错误信息。**

### 4.3 错误信息里带 URL，就等于带密钥

FRED 的 key 在 query string 上。`f"HTTP {code} <- {url}"` 直接把密钥打进日志。
另外 `HTTPError` 对象**自身持有带密钥的完整 URL**，所以只改消息还不够 ——
必须 `raise ... from None` 切断异常链，否则打印 traceback 时会带出来。

### 4.4 Yahoo 不带 User-Agent 会 429

裸 `urllib.request.urlopen` 实测返回 `HTTP 429 Too Many Requests`。
带上 UA 后正常。这是非官方接口无 SLA 的具体表现。

### 4.5 日期格式不统一

CBOE 波动率 CSV 是 `MM/DD/YYYY`，Yahoo 是 `YYYY-MM-DD`。归一化层必须统一。

### 4.6 工具本身的假证据

- `curl -w '%{size_download}'` 配 `-o /dev/null` 在 Git Bash 下读到 `0B`，别拿它当"空响应"的证据。
- Git Bash 下 `/tmp` 可能不存在，临时文件放项目内目录（用完删）。

## 7. 迁移取舍：MVP 的哪个模块进哪一层

### 7.1 为什么 `derive/net_liquidity.py` 进 L1 而不是 L3

架构文档第 3 节把"净流动性因子"排在 L3，但那说的是**契约**：
`Panel → FactorReading`（带窗口、带标准化、能报出输入）。

MVP 里这个函数**不满足**该契约 —— 它接的是 `[(值, 单位, 符号)]`，只做"先换算再带符号求和"，
**没有窗口、没有标准化、不产出 FactorReading**。它是公式级原语，不是因子。

**取舍**：按它**实际是什么**（单位安全的公式原语）放进 `L1_接入层/derive/`，
并在文件头写明"L3 因子层将来在此之上做滚动标准化"。
若硬塞进 `L3_因子层/`，会让 L3 出现一个不符合 L3 契约的成员，
后来人照它写第二个因子就会以为"L3 不需要 Panel"。

> 架构文档第 9 节对 `mvp/` 的审计结论也是 "L0 基本完成 / L1 完成 / L2–L7 未开始" ——
> 即 `mvp/` 里的一切都属 L0 或 L1。本次迁移与该结论保持一致。

### 7.2 为什么 `fetch_all.py` 进 `tools/` 而不是 L2

它的 docstring 原文自称 L2，但架构文档里的 L2 是**归一化层**（align / convert / staleness / panel_store），
产物是 `Panel`。而 `fetch_all` 干的是"依次调 L1 适配器 → 落盘 JSON → 汇总退出码"，
**没有任何归一化语义**，也不产出 Panel。

**取舍**：放进 `tools/`（非分层驱动脚本）。理由：它不是层，是**入口**；
放进 L2 会让 L2 的第一个成员就违反 L2 的契约。同理 `units_selfcheck` → `tools/selfcheck.py`。

### 7.3 `tools/` 为什么被 `check_layering.py` 排除

`tools/` 按设计是横向消费者，允许依赖任意层（它要能同时调 L1 和将来调 L2–L5 做重放）。
如果把它纳入"只能 Ln → L(n-1)"的规则，驱动脚本就没法工作。

**代价（明说）**：`tools/` 因此成为唯一能绕过 L2 直接调 L1 的地方。
若将来把业务计算写进 `tools/`，单向依赖会名存实亡。这是**有意接受的缺口**，
不是漏检 —— 校验脚本的输出里写明了"排除 tools/"。

### 7.4 为什么 `config.py` 的根锚点没改结构

MVP 里是 `MVP_ROOT = Path(__file__).resolve().parent.parent` → `mvp/`。
新位置 `L0_基元层/config.py` 的**上两级恰好也是仓库根**，所以只需把常量改名为 `REPO_ROOT`，
`parent.parent` 原样不动。**没有引入 `os.environ` 覆盖、没有 `sys.path` 猜测** ——
那类"自动找根"的写法会在测试与部署下给出不同的根，是隐性分歧源。

### 7.5 中文目录名：实测过才敢用

先建 `_nametest/` 探针验证，确认三件事后才落盘：
- `import L0_基元层.units` 成立（PEP 3131，CJK 不受 NFKC 归一化影响）；
- `python -m tools.fetch_all` 这种"包路径带中文"的调用方式成立；
- 带**空格**的目录名**不成立**（已排除，未采用）。

探针目录用完即删，不留残留。

### 7.6 迁移保真性怎么证明的（方法取舍）

**不用**"重跑一遍 MVP 测试看它绿不绿"当证据 —— 那只证明参照实现自己没坏。
实际用两层：

1. **函数体 AST 逐函数比对**（而非整文件文本 diff）。
   理由：路径、注释、行序变了都不该算行为变化，而函数体内部任何逻辑改动必须现形。
   文本 diff 会把 9 个模块全部标红，等于没有信号。
   比对结果 3 处差异，**逐一申报并写明理由**；白名单外出现任何差异即 FAIL，
   白名单里声明了但实际不存在的差异也 FAIL（防止白名单腐烂）。
2. **差分行为比对**：同一批输入喂给新旧两个实现，只比**公开函数的返回值**，
   625 组全等。含异常路径（跨族换算、缺 observations、正则未命中、非法符号），
   比较的是异常**类型名**而不是消息文本。

**明说这套方法不能证明什么**（写在脚本 docstring 里，避免过度外推）：
- 不能证明 L2–L7 —— 那些层还没有参照实现；
- 不能证明网络层等价 —— 只比解析函数在固定输入下的输出；
- **不能证明新实现"对"** —— 只证明新旧一致。参照实现若有错，两边一起错。

### 7.7 变异反证怎么做的

只跑"全绿"不能下结论。三个变异分别打在三处不同性质的缺陷上：

| 变异 | 打在哪 | 期望报红的是 | 结果 |
|---|---|---|---|
| 脱敏失效（`_scrub` 空操作） | L0 安全属性 | `port_fidelity` + `tools.selfcheck` | 两者 RC=1 ✓ |
| 换算系数 ×1001 | L0 算术正确性 | `port_fidelity` + `tools.selfcheck` | 两者 RC=1 ✓ |
| 同层互相 import | L1 依赖方向 | `tools.check_layering` | RC=1 ✓ |

**注意第 2 行的一个副产品**：换算系数错时 `check_layering` **仍然 RC=0**。
这不是漏检，是分工正确 —— 它只管结构，不管算术。
**记录这一点，是为了防止将来有人拿"layering 绿了"去证明"算术没问题"。**

变异前先 `cp` 备份到 `data/.mutbak/`，变异后 `diff` 确认还原干净（diff 为空），再复跑确认转绿。
`data/.mutbak/` 用完即删。
