## 2. 事实更正（全部实测，附原始输出）

### 2.1 CBOE 页面**不是** `__NEXT_DATA__`

建议原文：「CBOE 改为 Next.js 架构后，数据打包在 HTML 的 `__NEXT_DATA__` JSON 节点中」。

```
含 __NEXT_DATA__        : False
含 self.__next_f.push   : True
出现次数 __next_f.push  : 45
PCR 数据在 next_f 块内  : True
```

CBOE 用的是 Next.js **App Router + RSC payload**（`self.__next_f.push`），**不是** Pages Router 的 `__NEXT_DATA__`。
→ **按建议写解析器会直接失败。** 这条必须更正，否则 L1 适配器第一行就错。

### 2.2 TGA（`WTREGEN`）**不是日频**

建议原文：「TGA 与 RRP 是每日真实更新的」「TGA 缴税抽水会忠实反映在日频斜率上」。

```
WTREGEN     frequency='Weekly, Ending Wednesday'   units_short='Mil. of U.S. $'
WALCL       frequency='Weekly, As of Wednesday'    units_short='Mil. of U.S. $'
RRPONTSYD   frequency='Daily'                      units_short='Bil. of US $'
WTREGEN 最近 6 个观测日期: 2026-10-07, 2026-09-30, 2026-09-23, 2026-09-16, 2026-09-09, 2026-09-02
```

三个量里**只有 RRP 是日频**。`WALCL` 与 `WTREGEN` 都是周频（间隔 7 天）。
→ 建议用"TGA 日频抽水"论证 `ΔNetLiq_5D` 有实战意义，**论证前提不成立**。
→ 真实情况：多数交易日里 `Δ5D` 只由 RRP 驱动，而当前 RRP 仅 **0.201 十亿**，几乎不动。这个指标目前是"几乎恒定"的。

### 2.3 Yahoo **没有** PCR 代码

建议原文：「备选从 Yahoo Finance 拉取 `^PCR`（若有）」。

```
%5EPCR         -> HTTP 404 不存在
%5EPCALL       -> HTTP 404 不存在
%5ETOTALPC     -> HTTP 404 不存在
%5EEQUITYPC    -> HTTP 404 不存在
%5EPPUT        -> 存在
```

但 `^PPUT` 的名称是 **"CBOE S&P 500 5% Put Protection"**，值 2211.62 —— 是一个保护策略**指数**，不是看跌看涨比。
→ **这条路不存在**，CBOE 页面解析没有免费替代源。

### 2.4 `BAMLC0A0CM` **不是** ICE 3 年限制的解

建议原文：「信用维度接入历史更长的替代序列（如 `HYG/LQD` 相对价格比值或 `BAMLC0A0CM` 投资级利差）」。

```
BAMLC0A0CM 最早可得观测: 2023-10-16
```

与 `BAMLH0A0HYM2` 完全相同 —— **它也是 ICE BofA 系列，同样 3 年、同样"禁止再分发"条款**。用它替代等于没替代。

`HYG/LQD` 实测可得（HYG 76.81 / LQD 102.66），方向可行，**但要注意久期错配**：
LQD 久期约 8 年、HYG 约 3 年，两者价格比会被利率变动污染，不是纯信用利差。用作"信用压力"代理需要先剔除利率因子，或改用久期匹配的口径。

### 2.5 `VCT ≥ 1.00` **不是**自然边界

$$VCT = 0.6 \times \frac{VIX9D}{VIX} + 0.4 \times \frac{VIX}{VIX3M}$$

`VIX/VIX3M` 长期 **< 1**（contango 是常态，今日实测 0.898）。反推：

```
VCT = 1.00  ⇒  VIX9D/VIX ≈ 1.07
```

和原来的 1.05 几乎一样。把 0.90 / 0.92 / 0.95 换成 1.00，**只是换了个魔数，没有变成自然边界**。

真正有自然边界的量是 **`VIX9D/VIX ≥ 1.00`**（近月波动率不低于 30 日）—— 这才有"平价"含义。
→ 建议：条件直接写 `VIX9D/VIX ≥ 1.00`；VCT 若要保留，应相对其**滚动中位数**衡量，而不是与 1.00 比。

## 3. 与项目规则冲突，建议拒绝

### 3.1 「解析失败沿用 T-1 状态并触发黄色告警」—— 违反 NO-FALLBACK-BEHAVIOR

这条的具体危害比"违反规则"更严重：**本系统的全部价值就是识别 regime 切换**。
用 T-1 的 PCR 冒充当日值，恰好会在切换发生的那一天把信号抹平 —— 而那天正是唯一重要的日子。

**正确做法**：
- 当日取数失败 → **fail-closed，明确报错，不出分**；
- 缓存（Parquet 冷备）只用于**回补重试**，不用于对外提供当日值；
- 告警等级应为红色，不是黄色。

### 3.2 在代码里写 `WALCL/1000 - WTREGEN/1000 - RRP` —— 手写换算系数

这正是 `mvp/src/units.py` 要消灭的反模式。目标单位一旦调整，要满仓库找 `/1000`。

**正确做法**：`units.convert(value, src_unit, dst_unit)`，目标单位从配置读。**已实现**，不改。

### 3.3 目标单位：十亿 vs 百万

我方 MVP 现为 `USD_MILLION`。改十亿需转换 2 个序列（WALCL、TGA）；改百万只需转换 1 个（RRP）。
两者在 `Decimal` 下都精确，但**百万让两个主导项保持整数**，可读性更好。

→ 建议保留百万。这是配置项，随时可改，**不是架构决策**，不值得为此改动代码。

### 3.4 「满足即计入该维度满分（25 分）」—— 二元满分会放大跳变

白皮书原本给的是 20–25 的**区间**。改成 0/25 二元后：
- 分数在阈值两侧跳变 25 分；
- 该维度对单一阈值判断的敏感度被放大到最大；
- 与 L5 需要的"迟滞"设计直接冲突。

→ 分位数方案下应输出**连续分**，不是 0/25。

## 4. 阈值方案（Risk 1 & 2）评估

建议主张：**废弃写死的绝对阈值，全量转向滚动 252 日分位数 / Z-Score**。

**方向对**：确实能一次性消掉三套口径冲突、分数段非点值、覆盖空洞、不可回测这四个毛病。

**但不能当成零验证的解药**，有四个未处理的问题：

| # | 问题 | 说明 |
|---|---|---|
| 1 | **丢失绝对水平信息** | 信用利差、VIX 期限倒挂是有经济含义的绝对量。HY OAS 300bps 若恰是近一年 95 分位，分位数说"高危"、绝对水平说"宽松"；危机年份里 420bps 可能只是 40 分位 |
| 2 | **参数问题只是搬家** | 252 日窗口长度的任意性不比阈值小，同样需要回测标定。Risk 1（零验证）**没有被消除，只换了位置** |
| 3 | **趋势性 regime 下会失效** | 若 ΔPCR 一年内持续高位（长期对冲 regime），其滚动分位会始终接近中位，恰好抹掉"极端"这个信息 |
| 4 | **冷启动需 1 年数据** | 白皮书原有的 20D / 60D 窗口没有这个问题 |

→ **建议混合而非全量替换**：
- **有经济含义的绝对量**（HY OAS 水平、VIX 期限倒挂）→ 用绝对阈值；
- **相对定位类**（ΔPCR 分位）→ 用滚动分位。

并且无论用哪种，**Risk 1（零回测）仍然要靠重放骨架解决**，分位数替代不了回测。

## 5. 路线图评估

建议的 `L0 → L1 → L2 → L3 → L4` 里**缺了重放骨架**，把 L3（含分位数计算）排在验证能力之前 ——
这正好会重演白皮书"阈值无法证伪"的病。

**我方既定顺序**（见 `docs/正式项目分层架构设计.md` 第 6 节）：

```
L0+L1 ✅ → L2 → 重放骨架 → L3(三个低风险维度) → 阈值标定 → L4 → gamma_proxy → L5 → L6 → L7
```

「先做 L2」这一点两边一致，可以推进。其余顺序需保持。

## 7. 下一步

建议中「可以直接批准推进 L2 归一化层」与我方顺序一致，**可以推进**。
但推进前需先由 KAI 裁定：

1. 阈值方案走**混合**（绝对 + 分位）还是**全量分位**；
2. 周度序列的 Δ 定义节点（在周更新点上算，还是保留日度但接受重复）；
3. 信用维度回测窗口（ICE 仅 3 年；若用 HYG/LQD 代理，需先定久期错配的处理方式）。

第 3 条新增了一个此前没识别到的问题：**若采用 HYG/LQD 代理，代理与实盘用不同序列，回测结论不能直接迁移到实盘** —— 需要在文档里显式声明这条边界。
